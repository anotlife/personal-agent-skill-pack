# Independent Oracles

## Principle

An oracle detects implementation errors only when it differs materially from the implementation. A check that reuses the implementation's own assumption, helper, parser, or expected value confirms the wrong thing with high confidence.

## Strong oracles

- Run the repository's established test suite instead of asserting your own expected output.
- Compare a numerical result against an independently derived formula, a second implementation, or published data.
- Parse a generated document with a different reader than the one that wrote it.
- Open a produced artifact in the real viewer, not a text dump of it.
- Compare a migration against a known-good fixture, schema, or production snapshot.
- For a UI change, exercise the user-visible path in a browser rather than importing an internal function and printing a value.
- For a pure function, verify a property (round-trip, idempotence, invariant holds) rather than re-listing expected outputs.
- Cross-check a fact against a second, independent source with different provenance.

## Weak oracles that look strong

| Looks like a check | Why it is not |
|---|---|
| Re-reading the text you just wrote | Proves existence, not correctness |
| Expected output copied from the implementation | Circular |
| Same helper used to compute result and expectation | Shared bug in both sides |
| A screenshot that hides a broken interaction | Visual presence is not behavior |
| Golden file regenerated by the code under test | Encodes current behavior, including bugs |
| "It compiled" | Types and syntax are not semantics |
| Unit tests all mocked at the boundary you changed | Exercises the mock, not the contract |

## Cost ladder for choosing an oracle

1. A property assertion (cheap, catches most logic errors).
2. A second independent implementation of the critical calculation.
3. A round-trip through a different system (write → external reader → compare).
4. An end-to-end run of the real user path.

Pick the cheapest rung that could actually fail for the reason you care about.

## Escalate to an independent oracle when

- the output is exactness-sensitive (money, dates, serialization, hashing, coordinates, units);
- the change touches parsing, serialization, numerical logic, or external behavior;
- the cost of a false "done" claim is high;
- the same misunderstanding could affect both the implementation and the self-check.

## Failure of the verification itself

Distinguish two outcomes and report the right one:

- **The oracle ran and reported a failure** → the change is not verified. Report the failure and its output.
- **The oracle could not run** → the change is unverified. Report the obstacle. Do not convert "could not check" into "checked and fine".

## Checklist

- [ ] The oracle uses a different path, not the same code in a new wrapper.
- [ ] The expected value came from outside the implementation.
- [ ] I know whether the oracle ran, passed, failed, or was skipped.
- [ ] If the oracle errored, I reported the error rather than the absence of a failure.
